# Статьи РУСПЛАСТЗАВОДА в Strapi CMS

Оператор `rusplast-seo` публикует одну статью каждые четыре дня в 12:00 по Москве.
После сна обрабатывается только актуальный выпуск; интервал считается от
фактической публикации. Расписание GloPro/Яндекса не меняется.

## Процесс

1. `scripts/editorial-context.mjs` читает опубликованные товары, статьи и список
   PDF-документов из CMS. При недоступной CMS подготовка останавливается.
   Непроверенные рекламные описания исключены из фактического контекста.
2. Авторизованный локальный Codex CLI создаёт полезную статью по новому вопросу.
   Проверяются структура, ссылки, метаданные, точные цитаты источников и дубли тем.
   Отдельная сессия проверяет доказательства, пользу и самостоятельность вопроса.
   На этом этапе `image: generated-cover` — обязательный внутренний маркер.
   Редактор проверяет описание `imageAlt`; файл и ссылка CMS появляются после
   одобрения текста и не требуются от текстового этапа.
3. Проверенный текст сохраняется в SQLite до генерации изображения. Встроенный
   `image_gen` Codex CLI создаёт новую фотореалистичную предметную обложку по теме.
   Не используются сторонние API-ключи, стоковые замены и рисование кодом.
4. Проверяются новый путь из `generated_images`, уникальность SHA-256, PNG/CRC,
   размер 80 КБ–30 МБ, минимум 1400×800 и горизонтальная композиция. PNG копируется
   в архив выпуска. Отдельная сессия с изображением проверяет реалистичность,
   геометрию, соответствие теме и отсутствие вымышленных надписей/документов.
   Это автоматическая редакторская проверка, не экспертное подтверждение.
5. `scripts/publish-article.py --article ... --image ... --validate-only` проверяет
   контракт. После проверки ссылок фиксированный publisher передаёт JSON и PNG
   по действующему SSH-доступу в приватный CLI CMS. Текст не выполняется как код.
6. CMS полностью декодирует PNG, загружает его в **Media Library → Блог**, создаёт черновик,
   затем публикует статью. Сайт получает статьи, обложки и sitemap из CMS.
   Пересборка сайта для новой статьи не нужна.
7. Проверяются SHA-256 исходного JSON вместе с PNG, содержимое опубликованной
   записи, Media Library URL, HTML/H1 и sitemap. Только после этих проверок
   выпуск отмечается завершённым.

Статьи: Strapi → Content Manager → Статья. Обложки: Media Library → Блог.
Папка создаётся автоматически при первой загрузке, если её ещё нет.
Документы: Content Manager → Документ; PDF загружается в поле файла.
Старый `generated-articles.json` больше не используется для новых публикаций.

## Повтор и ручные изменения

После ошибки изображения повтор использует уже проверенный текст. После ошибки
публикации используются те же JSON и PNG. Хеш сохранённого изображения проверяется
снова. Если CMS уже приняла выпуск, повтор сверяет его без нового изображения
или повторной публикации. Для выпуска, уже отмеченного `published`, оператор
только читает CMS и подтверждает совпадение текста, manifest SHA-256, H1,
фактического `img src` и sitemap. Это работает и для выпусков до миграции,
у которых нет локальной сгенерированной обложки; их текущая обложка сохраняется.
Исходная дата публикации и расписание при таком повторе не меняются.
При повторе незавершённой CMS-публикации собственная обложка старого запуска,
оставшаяся в корне Media Library с исходным именем, переносится в **Блог**
без изменения URL и связи со статьёй. Папки и имена редактора сохраняются.
Ручной черновик и изменённая редактором статья никогда
не перезаписываются: несовпадение останавливает автоматический выпуск.
Не удаляйте `data/operator.sqlite3` и архив исходных изображений ради повтора.

## Условия

Mac включён; служба `ru.artel.operator`, интернет, вход ChatGPT в Codex и SSH
действуют. Панель: http://127.0.0.1:8790. Генерация использует лимиты ChatGPT.
В CLI требуется включённая встроенная возможность `image_generation`.
При недоступном image_gen или отклонённой обложке статья не публикуется.
Нет скрытой замены на обычную картинку и нет автоматического перехода на API.

Обе генерации ограничены временем и запускаются в read-only sandbox. Генератору
не передаются данные топливных операторов или ключи сайта. Запись CMS выполняет
отдельный фиксированный серверный скрипт; публичный API остаётся только для чтения.

Конфигурация: `operators/rusplast-seo.md`; обработчик: `operator_app/seo.py`.
Артефакты доступны в истории запуска: контекст, текст, редакционная проверка,
PNG, промпт/метаданные изображения, проверка изображения, квитанция публикации.
Журналы: `data/logs/service.log`, `service-error.log`, `seo-command-error.log`.
Ошибки провайдера/SSH сохраняются локально без выдачи служебных данных в панель.
Проверки: `.venv/bin/python -m pytest -q`.


## Ручная проверка без изменения расписания

Обычный `POST /api/run` с `operator_id: rusplast-seo` повторяет текущий выпуск.
Он не создаёт вторую новую статью за тот же период. Для технической проверки
генерации используется отдельный Python-процесс с `OPERATOR_DATA_DIR`, заданным
на отдельную рабочую папку **до импорта** модулей. `seo.prepare_article` выполняет
контекст → текст → текстовую проверку → реальную генерацию PNG → визуальную
проверку → `--validate-only`; сам по себе этот вызов ничего не публикует.
`seo._generate_cover` выполняет только этапы изображения для уже готовой статьи.
Живая база оператора и его расписание при изолированной проверке не используются.
